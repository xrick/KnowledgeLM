# DocAI 資料庫架構分析報告

**日期時間**: 2026-01-27
**分析者**: Claude (SuperClaude Framework)
**分析範圍**: skill_metadata.db 中 5 個表格
**分析依據**: 完整 schema 定義、實際資料樣本、23 個 Python 檔案的 SQL 引用、資料完整性檢查

---

## 問題 1：欄位命名是否造成系統誤判或錯誤

### 🔴 高風險：`skill_id` 語義混淆

**`skill_metadata.skill_id`** 的值實際上代表的是**一份文件 (document)**，而非一個 skill。例如：
- `skill_20251203_094135_d01fd9b0_src_00` → 這是「投資理財」下的一份 PDF
- `skill_20260113_061734_4209c143_8388d1` → 這是「六法全書-民法」下的一個子文件

但整個系統把它當作 `skill_id` 傳遞，導致：
- `skill_document_mapping.skill_id` 實際指向的是「文件」而非「技能」
- `skill_chunk_metadata.skill_id` 同理
- 開發者容易混淆：到底是在操作 skill 還是 document？

### 🔴 高風險：`parent_skill_id` 多型態外鍵

`skill_metadata.parent_skill_id` 指向 **3 種不同類型的值**：

| 值 | 實際指向 | 問題 |
|---|---------|------|
| `'root'` | 哨兵值（根節點） | 不是真正的 FK |
| `skill_20251203_054249_f333015b` | 一筆 `skill_heads` 的記錄 | 跨表引用 |
| `skill_20260113_061734_4209c143_8388d1` | 另一筆 `skill_metadata` 的記錄 | 同表自引用 |
| `skill_20251203_071733_2a43e5ac` | **不存在的記錄**（孤兒） | 資料不一致 |

這造成查詢時無法確定 `parent_skill_id` 應該 JOIN 哪張表，**增加程式碼複雜度和潛在錯誤**。

### 🟡 中風險：`head_id` 前綴不一致

| head_id | skill_name |
|---------|-----------|
| `head_20251204_072143_2d3e...` | 大語言模型大全 |
| `head_20251204_072143_4a90...` | 投資理財 |
| `skill_20251203_054249_f333...` | **六法全書-民法** ← 使用 `skill_` 前綴 |

這會造成用前綴判斷類型的邏輯失敗。

### 🟡 中風險：`processing_jobs` 的 PDF 專屬命名

欄位 `pdf_path`、`pdf_filename`、`pdf_size_bytes` 在系統已支援 DOCX、PPTX、TXT、MD 的情況下，名稱不再正確。雖然目前不會直接造成程式錯誤（Python 不管欄位名稱語義），但會增加維護成本和誤解風險。

### 🟡 中風險：`skills.py:2752` 查錯表

```python
SELECT skill_id FROM skill_metadata WHERE skill_name = ?
```
應該查 `skill_heads` 表（`skill_name` 在該表有 UNIQUE 約束），但卻查了 `skill_metadata`（同名可能有多筆記錄），可能返回錯誤的 `skill_id`。

### 🔴 高風險：`skill_chunk_metadata` 缺少 CREATE TABLE

在 `initialize_database()` 中**找不到** `skill_chunk_metadata` 的 CREATE TABLE 語句，但程式碼有大量 INSERT 操作。這代表此表可能是在某次手動 migration 中創建的，新環境部署時會直接失敗。

## 問題 2：現有設計是否滿足系統功能

### ✅ 功能層面：基本滿足

現有的 5 個表格確實支撐了系統的核心功能：

| 功能 | 支援狀態 |
|------|---------|
| Skill 定義與管理 (CRUD) | ✅ `skill_heads` |
| 文件上傳與關聯 | ✅ `skill_metadata` + `skill_document_mapping` |
| Chunk 級別的向量檢索 | ✅ `skill_chunk_metadata` |
| 大檔案斷點續傳 | ✅ `processing_jobs` |
| 3 層樹狀結構 (Head → Main → Attachments) | ✅ 透過 `head_id` + `parent_skill_id` |
| 多文件格式支援 (PDF/DOCX/PPTX/TXT/MD) | ⚠️ 功能可用，但命名是 PDF 專屬 |

### ⚠️ 存在的技術債

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| `skill_document_mapping` 的 CREATE TABLE 與 INSERT 不一致 | 🟡 | INSERT 使用 `document_name`, `document_path`, `total_pages` 欄位，但 CREATE TABLE 沒有定義這些欄位 |
| `skill_name` 冗餘存儲 | 🟢 | 同時存在於 `skill_heads` 和 `skill_metadata`，可能不同步 |
| 9 筆孤兒記錄 | 🟡 | `skill_document_mapping` 中有 9 筆 `skill_id` 指向不存在的 `skill_metadata` 記錄 |
| 1 筆 `parent_skill_id` 孤兒 | 🟡 | 指向 `skill_20251203_071733_2a43e5ac`，不存在任何表中 |

### 結論

設計**功能上可用**，但存在顯著的結構性技術債，隨著系統複雜度增加，維護成本會持續上升。

## 問題 3：更名是否提升效能與穩定

### 效能影響：❌ 無提升

SQLite 的查詢效能取決於**索引、查詢計畫和資料量**，與欄位或表格名稱完全無關。重新命名不會改變任何 I/O 或計算路徑。

### 穩定性影響：✅ 長期有提升，但 ⚠️ 短期有高風險

**長期穩定性提升**：
- 消除 `skill_id` 語義混淆 → 減少開發者犯錯機率
- 統一 `parent_skill_id` 指向規則 → 減少資料不一致
- `pdf_*` → `document_*` → 正確反映多格式支援
- 補齊 `skill_chunk_metadata` 的 CREATE TABLE → 新環境部署不會失敗

**短期風險**：

| 影響面 | 說明 |
|--------|------|
| **23 個 Python 檔案** | 包含 SQL 引用需要同步修改 |
| **前端 JavaScript** | `skill_main.html`、`skill_config.html` 引用了 API 回傳的欄位名稱 |
| **現有資料遷移** | 需要 migration script 處理已有的 17+ 筆 metadata 和 1600+ 筆 chunk 資料 |
| **API 相容性** | 外部呼叫者（如果有）的欄位名稱會改變 |

### 建議策略

**不建議現在全面重新命名**。建議分階段進行：

1. **立即修復**（低風險、高價值）：
   - 補齊 `skill_chunk_metadata` 的 CREATE TABLE ✅ 已完成
   - 修正 `skills.py:2752` 查錯表的問題 ✅ 已完成
   - 清理 9 筆孤兒記錄 ✅ 已完成
   - 統一 `head_id` 前綴（修正六法全書-民法的 `skill_` 前綴）✅ 已完成

2. **中期重構**（需要 migration plan）：
   - `processing_jobs` 的 `pdf_*` → `document_*`
   - `skill_document_mapping` 補齊缺失欄位定義

3. **長期架構**（需要完整 migration + 測試）：
   - `skill_metadata.skill_id` → `document_id`
   - `parent_skill_id` 拆分為明確的 `head_id` 引用
   - 消除 `skill_name` 冗餘存儲

## 總結

| 面向 | 結論 |
|------|------|
| **欄位命名誤判風險** | 🔴 存在。最大問題是 `skill_id` 語義混淆和 `parent_skill_id` 多型態指向 |
| **功能滿足度** | ✅ 基本滿足，但有結構性技術債需要處理 |
| **更名效益** | 效能無影響；穩定性長期有益但短期風險高，建議分階段進行 |
