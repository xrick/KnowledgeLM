## 3. 文字提取程式碼完整性分析

### 3.1 PDF 提取 ✅ 完整

- **位置**: `app/Services/input_data_handle_service.py:152-186`
- **函式庫**: PyPDF2 (`from PyPDF2 import PdfReader`)
- **返回值**: `(corpus: str, pages: int)` — 注意返回 tuple
- **Dependencies**: ✅ PyPDF2 已在 requirements.txt

### 3.2 DOCX 提取 ⚠️ 程式碼存在，dependency 未安裝

- **位置**: `app/Services/input_data_handle_service.py:187-225`
- **函式庫**: python-docx（optional import，有 graceful fallback）
- **Import 方式**:
  ```python
  try:
      from docx import Document as DocxDocument
  except ImportError:
      DocxDocument = None  # graceful fallback
  ```
- **返回值**: `corpus: str` — 注意：**不返回頁數**，與 PDF 返回格式不一致
- **提取邏輯**: 提取所有非空 paragraph，用 `\n\n` 連接
- **限制**:
  - ❌ 不提取表格內容（`doc.tables` 未處理）
  - ❌ 不提取頁首/頁尾
  - ❌ 不提取圖片中的文字
  - ❌ 不提取嵌入物件
- **Dependencies**: ❌ `python-docx` 未列入 requirements.txt

### 3.3 TXT/MD 提取 ✅ 程式碼完整

- **位置**: `app/Services/input_data_handle_service.py:227-255`
- **處理**: UTF-8 優先，fallback 到 latin-1
- **返回值**: `text: str` — 注意：**不返回頁數**，與 PDF 返回格式不一致
- **Dependencies**: ✅ 無外部依賴

### 3.4 PPTX 提取 ❌ 完全不存在

- **現有程式碼**: 無 `extract_text_from_pptx()` 方法
- **Dispatch**: `extract_text()` 未包含 pptx 分支
- **函式庫**: `python-pptx` 未安裝也未 import
- **注意**: 系統有 PPT-converted-PDF 偵測（`skills.py:1588-1652`），但這是偵測已轉為 PDF 的 PPT，不是直接處理 .pptx 檔案

### 3.5 返回值不一致問題

| 方法 | 返回值 | 格式 |
|------|--------|------|
| `extract_text_from_pdf()` | `(corpus, pages)` | **tuple** |
| `extract_text_from_docx()` | `corpus` | **str** |
| `extract_text_from_txt()` | `text` | **str** |

**影響**: `extract_text()` dispatch 方法調用者如果期望 tuple（如 PDF），處理 DOCX/TXT 時會出錯。需要統一返回格式。

## 6. Skills 系統的 PDF 處理 Pipeline 耦合分析

Skills 系統有獨立的 PDF 處理流程，深度耦合 PDF：

| 函式 | 位置 | PDF 耦合點 |
|------|------|-----------|
| `process_pdf_for_skill_streaming()` | skills.py:1523+ | 使用 PyPDF2 + PyMuPDF 直接處理 PDF |
| `producer_thread()` | skills.py:1408+ | 區分 PDF 模式 vs PPT-PDF 模式 |
| PPT 偵測 | skills.py:1588-1652 | 使用 PyMuPDF (fitz) 偵測 PPT-converted PDF |

**重要**: Skills 的上傳處理**沒有**使用 `InputDataHandleService`，而是直接在 endpoint 中處理。要支援多格式需要重構這部分邏輯。

## 8. 總結

### 系統現狀
1. **後端採用硬編碼方式**限制檔案格式，API Endpoint 層有 3 處 `.endswith('.pdf')` 直接寫死
2. **Service 層已有良好的配置化設計**，`ALLOWED_EXTENSIONS` 可擴充
3. **DOCX 提取程式碼已存在**但未啟用，且有返回值不一致問題
4. **PPTX 提取程式碼完全不存在**，需要新開發
5. **Skills 系統的 PDF 處理 pipeline 高度耦合 PDF**，需要額外的重構工作
6. **前端有 accept 限制**需要同步修改

### 修改前的風險評估
- **DOCX 支援**: 🟡 中風險 — 程式碼存在但未經驗證，返回值需統一
- **TXT 支援**: 🟢 低風險 — 邏輯簡單穩定
- **PPTX 支援**: 🔴 高風險 — 需要全新開發提取邏輯
- **返回值統一**: 🟡 中風險 — 需要確認所有調用者的期望
