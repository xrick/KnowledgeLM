# Issue: 要求完整文件資料內容導致 LLM Hallucination

**日期**: 2026-02-11
**嚴重度**: 🟡 中（非 Bug，RAG 系統固有限制）
**狀態**: 已分析，待優化
**觸發條件**: 用戶提問要求輸出完整文件全文

---

## 問題描述

用戶上傳 `test_道德經.docx`（老子《道德經》81 章完整內容），在 Skill Chat 中提問：

> 「請給我道德經全文」

系統回應前 2-3 章內容大致正確（但已有偏差），從第 4 章開始快速退化，最終從第 9 章起不斷重複：

```
第九章
不出戶，不出戶，不出戶。

第十章
不出戶，不出戶，不出戶。

...（重複至第四十八章）
```

### 4. RAG 檢索行為分析 → 問題根因

系統使用 **top-k retrieval**（預設 k=3~5），面對「請給我道德經全文」的查詢：

1. FAISS 只返回最相關的 3-5 個 chunks（約 3000-5000 字元）
2. LLM 的 context window 只收到部分章節
3. LLM 被要求生成 81 章完整文本，但 context 不足
4. 前幾章根據 retrieved context 生成（大致正確但已有偏差）
5. 後續章節 LLM 從「記憶」中捏造，最終退化為重複輸出

---

## 根因結論

**非程式碼 Bug** — 這是 RAG（Retrieval-Augmented Generation）系統的固有限制：

```
用戶提問: "請給我道德經全文" (要求 ~6654 字完整輸出)
    ↓
FAISS Retrieval: top-k=3~5 → 只返回 ~3000-5000 字 context
    ↓
LLM Context: 只看到部分章節
    ↓
LLM 生成: 前幾章 OK → 後續章節 hallucinate → 退化為重複
```

### Hallucination 退化模式

| 階段 | LLM 行為 | 品質 |
|------|----------|------|
| 第 1-3 章 | 根據 retrieved chunks 生成 | 🟢 大致正確 |
| 第 4-8 章 | 混合 context + 模型記憶 | 🟡 有偏差 |
| 第 9+ 章 | 完全 hallucination | 🔴 重複/捏造 |

---

## 影響範圍

- **所有「要求完整全文」類型的查詢** 都會觸發此問題
- 文件越長，hallucination 越嚴重
- 短文件（< top-k 能覆蓋的範圍）不受影響

---

## 改善方向

### 方案 A: 增加 top-k（短期）

對於小文件（如道德經，只有 8 個 chunks），可以考慮增加 top-k 值，使 retrieval 能覆蓋全部 chunks。

- **優點**: 簡單、立即見效
- **缺點**: 大文件時 context window 可能超限；增加 token 成本
- **適用**: 小型文件（< 20 chunks）

### 方案 B: Prompt 引導（短期）

在 system prompt 中加入限制：

```
如果用戶要求輸出完整文件全文，請回覆：
「文件內容較長（共 N 字元），建議您分段查詢特定章節，或使用文件下載功能獲取完整內容。」
不要嘗試從記憶中生成文件中不存在的內容。
```

- **優點**: 防止 hallucination，改善用戶體驗
- **缺點**: 可能過度限制合理的查詢

### 方案 C: 全文下載功能（中期）

提供文件原文下載連結，讓用戶直接獲取完整內容。

- **優點**: 用戶確實能拿到完整全文
- **缺點**: 需要新增 API 和 UI 元素

### 方案 D: 智能 Retrieval 策略（長期）

根據查詢意圖動態調整 top-k：
- 偵測「全文」「完整」「所有」等關鍵字 → 增加 k 值或返回全部 chunks
- 一般查詢 → 維持 top-k=3~5

- **優點**: 精準、兼顧品質和成本
- **缺點**: 實作複雜度較高

---

## 建議優先順序

1. **方案 B（Prompt 引導）** → 最快實施，防止用戶看到 hallucination
2. **方案 A（增加 top-k）** → 小文件時可選
3. **方案 D（智能策略）** → Post-demo 長期優化
4. **方案 C（下載功能）** → 依產品需求決定
